## 4. What this changes in our core

- (evidence) The best-documented pattern for permissions at scale is: ACL as filterable metadata on every chunk, plus a separate query-time check for sources whose permissions change fast. Onyx does both (ACL filter in the index, `post_query_censoring.py` after retrieval). Notion stores permissions on every span and patches them without re-embedding. Our core should keep text hash and ACL hash separate.
- (evidence) For petabyte scale, the proven design is an object-storage-first vector and BM25 store with per-tenant namespaces. turbopuffer lists 3 PB+ and 1 trillion+ documents "seen", and Notion cut cost about 60% on search spend moving a multi-billion workload to it. Build our own store only if self-hosting is a hard requirement. If it is, pick Vespa, since it is the only open-source engine here with a billion-vector run and a stated cost (11 nodes, $6,038 a month on the 2022 benchmark).
- (evidence) Do not use pgvector as the core. It is one Postgres instance, filters after the index scan, and the README says a shared index lets one tenant's vectors affect another's recall. Keep it for the small graph and metadata side only.
- (evidence) Do not adopt Onyx, Airweave or Graphiti as the core. Onyx keeps permission sync in an enterprise-licensed folder, Airweave is archived, and Graphiti covers memory, not document search. Use them as reference designs and, for Graphiti, as the chat-memory layer.
- (evidence) Keep a hybrid index and do not replace it with live MCP calls. Dropbox reports live fan-out is slow and uneven and chose an index. Onyx found its indexed Slack connector beat Slack's search API. Keep a live-fetch lane for fresh or unindexed apps (Scout and Onyx federated connectors show how), and use it for last-mile permission checks.
- (evidence) Add chunk context before indexing, as Anthropic does (50 to 100 tokens per chunk, top 150 reranked down to 20). At petabyte scale the one-time cost matters: Anthropic quotes about $1.02 per million document tokens with prompt caching, so budget for it per source.
- (our inference) Index size should be set by chunk count, not source bytes. 1 billion 768-dim float32 vectors is about 3 TB raw, so at turbopuffer's top storage rate of $0.33 per GB that is roughly $1,000 a month before queries. This is our arithmetic and was not benchmarked. Quantization (binary, 2-bit, halfvec) is the biggest lever, but vendor tests show worse recall at the top end.
- (our inference) Do not build a graph database for company data. Dropbox tried one and moved the graph into async "knowledge bundles" in the normal index. Keep the graph small, built offline, and indexed like any other document.
